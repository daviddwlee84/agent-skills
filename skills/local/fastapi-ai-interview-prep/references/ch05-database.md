# Chapter 5 — Databases with SQLAlchemy, SQLModel, Alembic

Read this when prepping persistence, sessions, migrations, and pooling. Questions
are original; topics follow the book.

### Q1. Explain the N+1 query problem, how to detect it, and `selectinload` vs `joinedload`.

N+1 is one query for N parents plus one per parent when a relationship lazy-loads
(N more queries), usually inside a loop touching a relationship. Detect it by logging
SQL or asserting query counts in tests. `selectinload` issues a second `IN (...)`
query — best for collections (no row fan-out); `joinedload` uses a single JOIN —
best for to-one relationships. Match the strategy to cardinality.

### Q2. Size connection pools for 8 pods × 4 workers against Postgres `max_connections=200`. What breaks, and where does PgBouncer fit?

Total connections = pods × workers × pool size. 8×4×10 = 320 > 200, so the newest
workers fail to connect (the first breakage). Either shrink the per-worker pool, or
put PgBouncer (transaction pooling) in front so many app connections multiplex onto
few DB connections. Also enable `pool_pre_ping` so stale connections are replaced.

### Q3. Design the transaction boundary for "create order, decrement inventory, enqueue confirmation email."

Create-order and decrement-inventory must be in one DB transaction (atomic; the
inventory decrement guards against oversell with row locking or a conditional
update). The email must NOT be in the transaction — enqueue it via the
transactional-outbox pattern (write an outbox row in the same transaction, a worker
sends after commit), so a rollback never sends a phantom email and a send failure
never rolls back the order.

### Q4. Zero-downtime column rename: how, and why is `alembic revision --autogenerate` alone insufficient?

Autogenerate sees a rename as drop-old + add-new, which loses data and breaks
running code mid-deploy. Do it in stages: add the new column (nullable) and deploy;
backfill + dual-write old and new; switch reads to new; stop writing old and drop it
in a later migration. Review every autogenerated migration; it can't infer renames or
data migrations.

### Q5. SQLModel vs plain SQLAlchemy + separate Pydantic schemas for a growing service.

SQLModel reduces boilerplate (one class for table + schema-ish) and is pleasant for
small/medium services, but blurs the request/storage/response separation as models
grow. SQLAlchemy + separate Pydantic schemas is more ceremony but keeps the three
roles clean, which scales better when API and storage shapes diverge. Either way,
hide the store behind a repository.

### Q6. What does session-per-request guarantee, and what goes wrong with a module-level global session?

Session-per-request gives each request an isolated unit of work that commits or rolls
back together and is cleaned up afterward. A module-global session is shared across
requests/threads, leaks state and identity-map entries, and breaks under concurrency
with confusing, intermittent errors.

### Q7. Why is `pool_pre_ping` (or equivalent) needed in cloud deployments?

Cloud databases and proxies drop idle connections (idle timeouts, failovers,
maintenance). Without pre-ping, the pool hands out a dead connection and the request
errors. `pool_pre_ping` issues a cheap liveness check and transparently replaces a
stale connection before use.

### Q8. What's the difference between `flush()` and `commit()`, and when do you need explicit flush?

`flush()` sends pending SQL to the DB within the current transaction (so you can read
a generated primary key or trigger constraint checks) without ending it; `commit()`
makes changes durable and ends the transaction. You need explicit `flush()` when you
need a generated id mid-unit-of-work before committing.

### Q9. Reads are 20× writes and reporting queries are degrading checkout latency. Options?

Route heavy/reporting reads to a read replica; add appropriate indexes or
materialized views; cache hot read results; separate the reporting workload onto its
own connection pool or service so it can't contend with transactional checkout. The
goal is to stop analytical reads from sharing fate with latency-critical writes.

### Q10. How would you make repository-layer code testable without mocking SQLAlchemy internals?

Define a repository interface and test the service against a fake/in-memory
implementation; for the real repository, run integration tests against SQLite
in-memory (and a marked Postgres tier for dialect-sensitive behavior) rather than
mocking sessions/queries. You test real SQL behavior cheaply instead of asserting on
mock call sequences that break on refactor.
