## Engine, session, unit of work

- **Engine** — one per process, created at startup (in `lifespan`). Owns the
  connection pool. Never create an engine per request.
- **Session** — one per request, sourced via a `yield` dependency (see
  `architecture-di.md`). A session is a unit of work: a staging area for changes
  that commit together or roll back together.
- **Unit of work** — do the related reads/writes in one session, `commit()` once at
  the end (or roll back on error). A request that commits halfway through leaves
  partial state on a later failure.

Use SQLite for local dev and PostgreSQL for production, but test dialect-sensitive
behavior against real Postgres (see `testing.md`) — SQLite hides typing laxity,
concurrency, and dialect SQL.

## SQLModel vs SQLAlchemy

- **SQLModel** (one class, both ORM table and Pydantic-ish schema) reduces
  boilerplate and is pleasant for small/medium services. The cost: the single
  class blurs the request/storage/response separation, so you still define
  separate read/create/update schemas as the model grows.
- **SQLAlchemy + separate Pydantic schemas** is more ceremony but keeps the three
  schema roles cleanly separate, which scales better for a large service with
  diverging API and storage shapes.

Default to SQLModel for a new service; reach for explicit SQLAlchemy + Pydantic
when the model count and divergence grow. Either way, **hide the store behind a
repository interface** so swapping is an implementation detail.

## N+1 and eager loading

The N+1 problem: you fetch N parent rows, then lazy-loading a relationship fires
one extra query per parent (N more queries). It hides in loops that touch a
relationship attribute. Detect it by logging SQL (`echo=True` in dev) or with a
query-count assertion in tests.

Fix with eager loading, choosing the strategy by relationship shape:

| Strategy | Mechanism | Best for |
|---|---|---|
| `selectinload` | Second `IN (...)` query | Collections (one-to-many); avoids row fan-out |
| `joinedload` | Single `JOIN` | To-one relationships; one round trip |

`joinedload` on a collection multiplies rows (cartesian fan-out); `selectinload`
on a to-one adds an unnecessary second query. Match the tool to the cardinality.

## Alembic migrations

`alembic revision --autogenerate` diffs models against the DB and drafts a
migration — but **review every autogenerated migration**: it misses data
migrations, can't infer safe column renames (it sees drop-old + add-new, which
loses data), and may reorder operations dangerously.

Zero-downtime column rename is a multi-deploy dance, not one migration:

1. Add the new column (nullable), deploy.
2. Backfill + dual-write old and new, deploy.
3. Switch reads to the new column, deploy.
4. Stop writing the old column; drop it in a later migration.

Run migrations (`alembic upgrade head`) as a deploy step, and test the migration
chain in CI (run the migrations, not just `create_all`).

## Connection pool sizing

Total connections = pods × workers-per-pod × pool size. This must stay under the
database's `max_connections`. Example: 8 pods × 4 workers × pool 10 = 320
connections — which blows past a Postgres `max_connections=200` and the newest
workers fail to connect. Either shrink the pool, or front Postgres with
**PgBouncer** (transaction pooling) so many app connections multiplex onto few DB
connections. Enable `pool_pre_ping` in the cloud so stale connections (killed by
an idle timeout or failover) are detected and replaced instead of erroring.

## Gotchas

- **`flush()` is not `commit()`.** `flush()` sends pending SQL (so you can read a
  generated id) within the transaction; `commit()` makes it durable and ends the
  transaction. You need an explicit `flush()` when you need the id mid-unit-of-work.
- **A module-level global session is a bug.** It's shared across requests/threads,
  leaks state, and breaks under concurrency. Always session-per-request.
- **`selectinload` vs `joinedload` chosen wrong** degrades the exact query you were
  trying to speed up — pick by cardinality, then verify the SQL.
- **Autogenerated migrations are a draft, not a deploy artifact.** Review them; a
  blind `--autogenerate` rename silently drops a column's data.
- **Read-heavy reporting can starve transactional latency.** Route heavy reads to a
  replica or a separate connection pool rather than letting them contend with
  checkout writes.
