# Experiments and the queue

> Authoritative source: https://dvc.org/doc/user-guide/experiment-management and https://dvc.org/doc/command-reference/exp and https://dvc.org/doc/command-reference/queue

The single most useful DVC feature for ML work, and the one users most often misuse.

## Mental model: experiments are ephemeral commits

Every `dvc exp run` creates an **ephemeral commit** under `refs/exps/...` (a custom git ref namespace). It bundles:

- The state of `dvc.yaml`, `params.yaml`, source code at run time
- The actual contents of `outs`, `metrics`, `plots` (via DVC cache)
- The metric values, accessible via `dvc exp show`

Ephemeral commits don't pollute your branches. They're garbage-collected by `dvc exp gc` and only become "real" if you explicitly `dvc exp apply` or `dvc exp branch`.

This is why DVC can be a **local experiment tracker without a server**: git is the database, the cache is the artifact store.

## Single runs

```bash
dvc exp run                          # run pipeline with current params
dvc exp run -n my-baseline           # name it (default is autogenerated)
dvc exp run -S model.lr=1e-3         # override one param (dot-notation into params.yaml)
dvc exp run -S model.lr=1e-3 -S model.epochs=50   # multiple overrides
dvc exp run -s train                 # only re-run from `train` stage onward
dvc exp run --reset                  # ignore cache, re-run everything
```

`-S` (set) is the experiment-only override — it modifies params **for this run only** without touching `params.yaml` on disk.

## Sweeps with the queue

Two-step process: enqueue, then start workers.

### Enqueue

```bash
# Each --queue invocation enqueues ONE experiment:
dvc exp run --queue -S model.lr=1e-4
dvc exp run --queue -S model.lr=5e-4
dvc exp run --queue -S model.lr=1e-3
```

For grids, generate the calls in a loop:

```bash
for lr in 1e-4 5e-4 1e-3; do
  for bs in 16 32 64; do
    dvc exp run --queue -S model.lr=$lr -S train.batch_size=$bs
  done
done
# 9 experiments now sitting in the queue
```

The bundled `scripts/queue-helper.sh enqueue` wraps this for cartesian products.

### Start workers

```bash
dvc queue start --jobs 3              # 3 parallel workers
dvc queue status                      # see what's running / queued / done
dvc queue logs <task-id>              # tail logs of one task
dvc queue kill <task-id>              # stop a running task
dvc queue stop                        # stop the worker pool (queued tasks survive)
dvc queue remove <task-id>            # remove a queued task
dvc queue remove --all --queued       # clear the entire queue
```

**`dvc queue start` daemonizes.** Closing your shell does not stop the workers. Use `dvc queue stop` to shut them down cleanly.

### Inspect results

```bash
dvc exp show                          # rich table (current branch + all experiments)
dvc exp show --csv                    # parseable
dvc exp show --csv --no-pager | column -t -s,  # human-readable in terminal
dvc exp show --only-changed           # hide params/metrics that didn't vary
dvc exp show --rev HEAD~3..HEAD       # restrict to a commit range
```

For programmatic access:

```python
import dvc.api
exps = dvc.api.exp_show()             # list of dicts
```

## Promoting an experiment to a real commit

By default, ephemeral experiments stay in `refs/exps/`. To make one permanent:

```bash
dvc exp apply <exp-name>              # check out the experiment into the workspace
git add . && git commit -m "Promote <exp-name>"
dvc push                              # upload its artifacts to remote

# OR create a branch from the experiment without touching workspace:
dvc exp branch <exp-name> <branch-name>
```

Use `dvc exp show` (or `dvc exp ls`) to find the auto-generated experiment name (e.g., `funny-cats`).

## Garbage collection

Ephemeral commits accumulate. Clean periodically:

```bash
dvc exp remove <exp-name>             # one specific experiment
dvc exp remove --queue                # clear the queue only (keep finished)
dvc exp gc --workspace                # keep only experiments in workspace HEAD
dvc exp gc --all-tags --all-branches  # keep experiments derived from any tag/branch
```

`dvc exp gc` is destructive. Use `--dry-run` first.

## How metrics get bound to commits (the killer feature)

Because each experiment IS an ephemeral commit:

- `dvc metrics show --rev <exp-name>` returns the metrics for that exact run
- `dvc metrics diff <exp-a> <exp-b>` compares any two experiments
- `dvc plots diff <exp-a> <exp-b>` overlays plots from two runs
- `git log --oneline <exp-ref>` shows the commit that produced a metric

You never have to wonder "which code produced metric X" — the answer is a `git checkout` away.

## Common pitfalls

- **`--queue` without `start`** — Queued experiments don't run until `dvc queue start`. The CLI gives no warning.
- **Trying to `dvc exp run -S list=...`** — Param overrides are scalar. Use `dvc.api.params_show` + a wrapper script for complex overrides, or use `foreach` in `dvc.yaml`.
- **Worker queue dies after `dvc queue stop` but tasks remain queued** — Restart with `dvc queue start --jobs N`; queued tasks resume.
- **`dvc exp run` re-runs even when nothing changed** — By design: experiments are about exploration, not caching. Use `dvc repro` if you want change-detection.
- **Two experiments with the same params produce different results** — Set seeds explicitly in your training code; DVC doesn't randomize anything itself.
- **`dvc exp push` exists but is for sharing experiments via git remotes**, not for pushing artifacts. Don't confuse with `dvc push`.

## Sharing experiments with collaborators

```bash
dvc exp push origin <exp-name>        # push the ephemeral commit + cache to git/dvc remote
# collaborator:
dvc exp pull origin <exp-name>
dvc exp apply <exp-name>
```

This requires both a git remote (for the ref) and a dvc remote (for the artifacts). Both must be set up first.
